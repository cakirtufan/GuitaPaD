# GuitaPaD Architecture

## 1. Project identity

GuitaPaD is evolving from a Python guitar pedalboard experiment into an **adaptive guitar tone-matching platform**.

The central problem is:

> Given a player's guitar DI signal and a target guitar tone, find an interpretable DSP configuration that moves the player's output toward the perceptual character of the target.

This is treated as a hybrid problem involving:

- real-time audio engineering
- digital signal processing
- virtual-analog modelling
- optimisation
- audio feature extraction
- machine learning
- perceptual similarity

The project should not become a black-box model that simply maps input audio to output audio without exposing how the tone is produced.

---

## 2. Core design principle

The central separation is:

```text
ML / optimisation decides WHAT parameters should change.
DSP decides HOW the audio is processed.
```

The real-time sound should continue to be generated by an explicit DSP graph.

Machine learning may:

- analyse reference tones
- create embeddings
- estimate starting DSP parameters
- classify tone families
- accelerate parameter search
- learn perceptual similarity
- adapt presets to different guitars/interfaces

It should not initially replace the entire signal chain with an opaque waveform-to-waveform neural model.

---

## 3. System layers

### Layer A - Audio I/O

Responsibilities:

- audio-interface selection
- input/output channel mapping
- sample rate
- buffer negotiation
- callback execution
- latency reporting
- stream errors
- hardware-specific workarounds

Current implementation:

```text
src/guitapad/audio/
```

Current validated setup:

```text
Audient EVO 4
ASIO
48 kHz
128-frame callback
```

This layer should eventually become device-configurable rather than Audient-specific.

---

### Layer B - Real-time DSP engine

Responsibilities:

- preallocated audio buffers
- effect-chain execution
- parameter smoothing
- meters
- safety handling
- deterministic callback behaviour

Real-time callback rules remain strict:

- no file I/O
- no GUI work
- no network access
- no blocking locks
- no uncontrolled allocation
- no heavy model training
- no slow optimisation

The live audio path must remain independent from offline ML and optimisation workloads.

---

### Layer C - Tone engine

The tone engine is the controllable signal-processing graph.

Target structure:

```text
Input calibration
        |
        v
Noise gate
        |
        v
Pre-EQ / tightening
        |
        v
Nonlinear preamp / amp stages
        |
        v
Tone stack
        |
        v
Power-amp shaping
        |
        v
Cabinet model
        |
        v
Microphone / spatial shaping
        |
        v
Post-EQ
        |
        v
Safety / output
```

Not every tone will require every block.

Each block should expose a small, meaningful parameter set.

All controllable parameters together form:

```text
theta = {
    input,
    gate,
    pre_eq,
    amp,
    tone_stack,
    power_amp,
    cabinet,
    mic,
    post_eq,
    ...
}
```

The DSP renderer can then be written conceptually as:

```text
y = DSP(x, theta)
```

where:

- `x` = player's DI
- `theta` = tone parameters
- `y` = rendered guitar tone

---

## 4. DI capture and reproducible testing

Raw DI recording is a core research feature, not merely a convenience.

The same performance can be reused for:

- DSP A/B tests
- parameter sweeps
- loss-function experiments
- ML dataset generation
- regression tests
- subjective listening tests

Current design:

```text
Audio callback
    |
    +--> live DSP
    |
    +--> preallocated raw DI buffer

recording stops
    |
    v
24-bit WAV written outside callback
```

Reference renders should always be reproducible from:

```text
DI + DSP version + parameter recipe
```

---

## 5. Reference analysis

A reference tone should be transformed into a representation describing perceptually useful characteristics.

Initial hand-designed features may include:

- multi-resolution spectrum
- log-magnitude STFT
- spectral envelope
- band energy
- spectral centroid
- spectral slope
- transient / onset shape
- RMS envelope
- crest factor
- dynamic compression
- harmonic structure
- high-frequency distortion content
- temporal decay

A later learned representation may supplement these features.

Conceptually:

```text
z_target = Analyse(reference)
```

and:

```text
z_current = Analyse(rendered_output)
```

The analyser must be designed for **guitar tone similarity**, not generic audio similarity alone.

---

## 6. Tone-matching objective

The matching problem is:

```text
theta* = argmin D(
    Analyse(DSP(DI, theta)),
    Analyse(reference)
)
```

A composite loss may eventually include:

```text
L =
    w_spectrum   * L_spectrum
  + w_envelope   * L_envelope
  + w_transient  * L_transient
  + w_dynamics   * L_dynamics
  + w_harmonics  * L_harmonics
  + w_perceptual * L_perceptual
```

The exact form of the loss should be determined experimentally.

A low numerical loss is not sufficient if listening tests disagree.

---

## 7. Optimisation strategy

Tone matching should initially run **offline**, not inside the real-time callback.

Possible progression:

### Stage 1 - deterministic search

Use the captured DI and repeatedly render candidates.

Possible tools:

- grid/coarse search for small parameter groups
- coordinate search
- evolutionary optimisation
- Bayesian optimisation
- CMA-ES or similar derivative-free methods

The exact optimiser should be selected based on observed parameter-space behaviour rather than preference.

### Stage 2 - learned initialisation

Once enough matched examples exist, train a model:

```text
reference representation
        +
DI / input representation
        |
        v
parameter estimator
        |
        v
initial theta
```

The optimiser then refines this estimate.

This creates a hybrid system:

```text
ML estimate
    |
    v
initial preset
    |
    v
DSP render
    |
    v
comparison
    |
    v
optimisation
    |
    v
final tone recipe
```

### Stage 3 - learned perceptual similarity

A learned embedding or ranking model may later improve the loss function using human listening preferences.

This should remain separate from the real-time DSP engine.

---

## 8. Personalisation and domain adaptation

A fixed preset does not produce the same tone for every guitarist.

Relevant differences include:

- pickup type
- pickup height
- guitar electronics
- strings
- playing dynamics
- tuning
- interface instrument input
- input gain
- converter behaviour
- monitoring system

Therefore GuitaPaD should treat the player's DI as part of the problem.

The desired mapping is:

```text
reference target
      +
player DI characteristics
      |
      v
personalised tone recipe
```

This is one of the main differences between GuitaPaD and a conventional preset library.

---

## 9. Full-mix references

A commercial recording may contain:

- multiple rhythm-guitar layers
- lead guitar
- bass
- drums
- vocals
- mastering EQ
- compression
- stereo processing
- ambience

Therefore:

```text
full song != isolated guitar target
```

A naïve optimiser may accidentally try to reproduce bass or drum energy using the guitar chain.

Development should therefore proceed in stages.

Initial matching target:

```text
isolated guitar
or
guitar-dominant short reference segment
```

Later options:

- source separation
- guitar stem extraction
- guitar-aware masks
- stereo-layer analysis
- confidence estimates

Full-mix matching is a later research problem, not an MVP assumption.

---

## 10. Cabinet and monitoring

Nonlinear guitar tone should not be judged as if distortion alone were the complete system.

A convincing high-gain guitar tone generally depends strongly on downstream spectral shaping.

Therefore amp/cabinet/microphone stages are part of the target architecture.

The project should avoid evaluating every nonlinear model directly through full-range playback and then assuming the clipping algorithm alone explains the result.

---

## 11. Tone recipes

A tone recipe should be:

- human-readable
- versioned
- portable
- inspectable
- shareable
- independent from copyrighted reference audio

Possible structure:

```json
{
  "schema_version": 1,
  "name": "High-gain rhythm reference",
  "engine_version": "0.x",
  "input_profile": {
    "trim_db": -4.8
  },
  "blocks": {
    "gate": {},
    "pre_eq": {},
    "amp": {},
    "cabinet": {},
    "post_eq": {}
  },
  "matching": {
    "reference_description": "user supplied",
    "score": 0.86
  }
}
```

Tone recipes should record enough metadata to reproduce the render.

## 12. Community architecture

Community contributions may eventually include:

```text
recipes/
hardware_profiles/
cab_models/
dsp/
matching/
benchmarks/
```

Useful community data:

- interface model
- guitar/pickup type
- sample rate
- buffer
- latency
- callback load
- matched recipe
- optional feature statistics
- subjective rating

Copyrighted source recordings should not be committed to the repository.

---

## 13. Separation of live and offline workloads

The architecture should explicitly maintain two execution domains.

### Real-time domain

```text
audio input
-> DSP(theta)
-> audio output
```

Requirements:

- deterministic
- low latency
- bounded work
- no training
- no optimisation loops

### Offline / analysis domain

```text
DI
+ reference
-> feature extraction
-> candidate rendering
-> optimisation / ML
-> saved theta
```

Once a tone is matched, only the final parameter recipe is needed for live playing.

This separation allows heavy analysis without compromising performance.

## 14. Long-term architecture

```text
                         REFERENCE AUDIO
                                |
                                v
                    +----------------------+
                    | Reference Analyser   |
                    +----------------------+
                                |
                           target embedding
                                |
                                v
+-------------+        +----------------------+        +------------------+
| Player DI   |------->| Tone Matcher         |------->| Tone Recipe      |
+-------------+        | ML + Optimisation    |        | theta            |
       |               +----------------------+        +------------------+
       |                                                      |
       |                                                      v
       |                                             +------------------+
       +-------------------------------------------->| Real-time DSP    |
                                                     | Engine            |
                                                     +------------------+
                                                              |
                                                              v
                                                        AUDIO OUTPUT
```

The architecture should permit the analyser, optimiser, and ML models to evolve without redesigning the low-latency engine.
